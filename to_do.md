   Done: Implemented proof of work over the complete candidate block header and validate the current block hash against the configured difficulty.
2. No need strict backward compatibility. Remove unnecessary redirects. Maintain code functionality.
   Done: Implemented removal of obsolete compatibility wrappers and legacy transaction fields; the app now uses its explicit UUID-based APIs and versioned storage format.
3. Transactions should be based on unique identifiers, not names, and these identifiers should be stored in each node,  broadcast when updated and cross-checked when transactions are created and broadcast.
   Done: Implemented persistent UUID user identifiers, user-registry broadcasts, and identifier/amount/balance checks for locally created, peer-broadcast, and committed transactions.
4. Add failed broadcast reports, so nodes know if their block or data has been rejected. If user list, node list or blockchain has been rejected, it can request other nodes for their versions so that it can update its own. This update functionality should run periodically to so that valid users are not rejected on outdated nodes.
   Done: Implemented per-peer acceptance/rejection/error reports, synchronization after rejected data, shared state endpoints, and startup plus 30-second periodic synchronization.
5. Add lightweight persistent storage to validate and manage user balances. This data is individual to each node and should be updated after each transaction block is created. Functions more similar to a bank balance, not like the bitcoin UTXO-model. Rejected blocks should revert updates (perform the reverse) since these transactions have not been performed.
   Done: Implemented atomic, versioned JSON state persistence with ledger-derived integer balances, overdraft validation, and balance updates only after a block validates and commits; rejected blocks leave balances unchanged. Administrative credits require the same `BLOCKCHAIN_ADMIN_TOKEN` secret on each node and an `X-Admin-Token` request header.
6. Lightweight storage should also be used to allow nodes to preserve state across sessions. Should also be able to request for updated user lists, node lists and blockchain to get upto speed in a new session. All this will be used to update its own storage.
   Done: Implemented per-node storage for identity, peers, users, pending transactions, chain, and balances in `data/node-{port}/state.json` using pathlib; new and restarted nodes synchronize peer state into that store.
7. Improve resolve functionality for all broadcasts (user lists, node lists, blockchain, etc). Use a better, more secure approach than just length checks.
   Done: Implemented resolution using full chain, proof-of-work, transaction, and balance validation plus cumulative-work ranking and a deterministic hash tie-break; user and node registries are validated and merged separately.
